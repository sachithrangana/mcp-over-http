# CRUD Service

Simple Spring Boot 3 REST CRUD service for a `Product` resource, backed by an in-memory H2 database.

## Run

```bash
mvn spring-boot:run
# different port:
mvn spring-boot:run -Dspring-boot.run.arguments=--server.port=8085
```

Requires JDK 21. If `java` isn't on your PATH:

```bash
export JAVA_HOME=/opt/homebrew/opt/openjdk@21/libexec/openjdk.jdk/Contents/Home
```

## Test

```bash
mvn test
```

## Endpoints

| Method | Path                 | Description            | Success |
|--------|----------------------|------------------------|---------|
| GET    | `/api/products`      | List all products      | 200     |
| GET    | `/api/products/{id}` | Get one product        | 200     |
| POST   | `/api/products`      | Create a product       | 201     |
| PUT    | `/api/products/{id}` | Replace a product      | 200     |
| DELETE | `/api/products/{id}` | Delete a product       | 204     |

Unknown ids return 404 and validation failures return 400, both as RFC 7807 problem details.

## Health

Spring Boot Actuator exposes a health check at `/actuator/health` (plus `/actuator/info`):

```bash
curl localhost:8080/actuator/health
# {"status":"UP","components":{"db":{"status":"UP",...},"diskSpace":{...},"ping":{"status":"UP"}}}
```

It returns 200 when every component is `UP` and 503 when any is `DOWN`, so it works directly as a
load balancer or container health probe. Component details are shown via
`management.endpoint.health.show-details=always` in `application.properties` — drop that line if you
would rather not expose internals publicly.

```bash
curl -X POST localhost:8080/api/products \
  -H 'Content-Type: application/json' \
  -d '{"name":"Chair","description":"Ergonomic","price":199.99}'
```

The H2 console is at `/h2-console` (JDBC URL `jdbc:h2:mem:crud`, user `sa`, empty password). Data is in-memory and resets on restart.

## Signing in from a browser

The service is its own OAuth2 authorization server and ships the two pages the authorization code
flow needs:

| Path | Purpose |
|------|---------|
| `/login`          | Username and password form |
| `/oauth2/consent` | Tick which permissions to grant this login |

They exist for the MCP plugin (`../mcp-server`), which signs in as a real user with authorization
code + PKCE. Two things are deliberate:

- **Consent is never remembered** (`PerLoginConsentService`), so granting `products.write` is a
  decision made at every login rather than once.
- **The token is capped at the user's own scopes** (`UserScopeJwtCustomizer`) as it is minted. The
  consent screen filtering out `products.write` for `bob` is presentation; this is the control that
  makes a forged consent submission useless.

Registered clients:

| Client | Type | Grants |
|--------|------|--------|
| `crud-plugin` | public, PKCE required | `authorization_code` |
| `crud-client` | confidential (`crud-secret`) | `client_credentials`, `password` |

## API docs (Swagger)

Interactive docs are generated by springdoc-openapi:

| URL | What it is |
|-----|------------|
| `/swagger-ui.html` | Swagger UI, interactive |
| `/v3/api-docs` | OpenAPI 3 document (JSON) |
| `/v3/api-docs.yaml` | Same document as YAML |

```bash
open http://localhost:8080/swagger-ui.html
curl -s localhost:8080/v3/api-docs | jq .
```

**Authenticate before calling anything.** Every operation needs a bearer token, so in Swagger UI
click **Authorize** first, choose the **password** flow, and sign in as a user (`alice`/`alice-secret`
for read and write, `bob`/`bob-secret` for read only). The client id and secret are prefilled. The
`clientCredentials` flow is offered too for machine-to-machine calls. Without authorizing, *Try it
out* returns **401**.

## OAuth2

The API is protected by OAuth2. The app is both the **authorization server** (issues JWTs) and the
**resource server** (validates them), so nothing external is needed.

Client: `crud-client` / `crud-secret`, scopes `products.read` and `products.write`. Two grants are
supported.

### password — a user's own credentials

Seeded users (in the `app_user` table, BCrypt hashed, recreated on every restart):

| User | Password | Scopes |
|------|----------|--------|
| `alice` | `alice-secret` | `products.read`, `products.write` |
| `bob` | `bob-secret` | `products.read` |

```bash
TOKEN=$(curl -s -u crud-client:crud-secret \
  -d grant_type=password -d username=alice -d password=alice-secret \
  --data-urlencode 'scope=products.read products.write' \
  localhost:8080/oauth2/token | jq -r .access_token)

curl -H "Authorization: Bearer $TOKEN" localhost:8080/api/products
```

The token's `sub` is the username, and it carries only scopes the user *and* the client are both
allowed — asking for more returns `invalid_scope`, and a bad password returns `invalid_grant`.

Note this grant is a local extension: the password grant was dropped in OAuth 2.1 and Spring
Authorization Server ships no implementation, so it is supplied by
`security/PasswordGrantAuthentication{Token,Converter,Provider}.java`. Prefer the authorization code
flow for anything real — the password grant hands the client the user's actual password.

### client_credentials — machine to machine

```bash
TOKEN=$(curl -s -u crud-client:crud-secret \
  -d grant_type=client_credentials -d 'scope=products.read products.write' \
  localhost:8080/oauth2/token | jq -r .access_token)
```

| Endpoint | Purpose |
|----------|---------|
| `POST /oauth2/token` | Issue an access token (HTTP Basic client auth) |
| `GET /oauth2/jwks` | Public keys used to verify tokens |
| `GET /.well-known/oauth-authorization-server` | Discovery document |

Access rules:

- `GET /api/**` requires scope `products.read`
- `POST` / `PUT` / `DELETE /api/**` require `products.write`
- `/actuator/health`, `/actuator/info`, `/v3/api-docs*` and `/swagger-ui/**` stay public so probes
  and the docs page work before you authenticate
- No token → **401**; valid token without the needed scope → **403**

Tokens last 1 hour. Demo user passwords are seeded in `UserSeeder` and the client secret lives in
`AuthorizationServerConfig`; both belong in secret management for anything real. The RSA signing key
is generated at startup, so a restart invalidates every
issued token — fine for a demo, but a real deployment should load a persistent key from a keystore
or secret manager, and keep the client secret out of source control.
